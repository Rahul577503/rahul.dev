# React Performance Optimization: A Complete Guide

_Published on January 3, 2026_

Performance is not just a feature—it's a fundamental requirement for modern web applications. In this comprehensive guide, we'll explore proven techniques to optimize React applications, understand the rendering lifecycle, and implement patterns that make your apps blazingly fast.

---

## Understanding React's Render Cycle

Before diving into optimization techniques, it's crucial to understand how React renders components. Every performance optimization strategy stems from this fundamental knowledge.

![React Render Cycle](/img/react-render-cycle.png)

### The Three Phases of Rendering

1. **Trigger Phase**: Something causes a re-render (state change, props change, parent re-render)
2. **Render Phase**: React calls your component functions and builds the Virtual DOM
3. **Commit Phase**: React updates the actual DOM with changes

**Key Insight**: The render phase is pure and can be interrupted, while the commit phase is synchronous and cannot be interrupted.

---

## The Re-Render Problem

One of the most common performance issues in React applications is unnecessary re-renders. Let's understand why this happens:

```tsx
function ParentComponent() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <button onClick={() => setCount(count + 1)}>Count: {count}</button>
      <ExpensiveChild /> {/* Re-renders even though it doesn't use count! */}
    </div>
  );
}

function ExpensiveChild() {
  // Expensive computation or rendering
  console.log("ExpensiveChild rendered");
  return <div>I'm expensive to render</div>;
}
```

**Problem**: Every time `count` changes, `ExpensiveChild` re-renders unnecessarily.

---

## Solution 1: React.memo - The Smart Wrapper

`React.memo` is a higher-order component that memoizes your component, preventing re-renders when props haven't changed.

![React Memoization](/img/react-memoization.png)

```tsx
const ExpensiveChild = React.memo(function ExpensiveChild() {
  console.log("ExpensiveChild rendered");
  return <div>I'm expensive to render</div>;
});

// Now ExpensiveChild only re-renders when its props change!
```

### When to Use React.memo

**Use it when**:

- Component renders often with the same props
- Component is expensive to render
- Component is a pure component (same props = same output)

**Don't use it when**:

- Props change frequently
- Component is cheap to render
- You're prematurely optimizing

## Solution 2: useMemo - Expensive Computations

`useMemo` memoizes the result of expensive computations, recalculating only when dependencies change.

```tsx
function ProductList({ products, filter }) {
  // Without useMemo: filters on every render
  // const filtered = products.filter(p => p.category === filter);

  // With useMemo: only filters when products or filter changes
  const filteredProducts = useMemo(() => {
    console.log("Filtering products...");
    return products.filter((p) => p.category === filter);
  }, [products, filter]);

  return (
    <div>
      {filteredProducts.map((product) => (
        <ProductCard key={product.id} product={product} />
      ))}
    </div>
  );
}
```

### Real-World Example: Search with Debouncing

```tsx
function SearchResults({ query }) {
  const [results, setResults] = useState([]);

  // Expensive search operation
  const searchResults = useMemo(() => {
    if (!query) return [];

    return performExpensiveSearch(query);
  }, [query]);

  return <ResultsList results={searchResults} />;
}
```

## Solution 3: useCallback - Stable Function References

`useCallback` returns a memoized callback function, preventing child components from re-rendering due to new function references.

```tsx
function TodoList() {
  const [todos, setTodos] = useState([]);

  // Bad: Creates new function on every render
  // const handleToggle = (id) => {
  //   setTodos(todos.map(t =>
  //     t.id === id ? { ...t, done: !t.done } : t
  //   ));
  // };

  // Good: Stable function reference
  const handleToggle = useCallback((id) => {
    setTodos(prev => prev.map(t =>
      t.id === id ? { ...t, done: !t.done } : t
    ));
  }, []); // Empty deps because we use functional update

  return (
    <div>
      {todos.map(todo => (
        <TodoItem
          key={todo.id}
          todo={todo}
          onToggle={handleToggle}  {/* Same reference every time */}
        />
      ))}
    </div>
  );
}

const TodoItem = React.memo(({ todo, onToggle }) => {
  console.log('TodoItem rendered:', todo.id);
  return (
    <div onClick={() => onToggle(todo.id)}>
      {todo.text}
    </div>
  );
});
```

## Advanced Pattern: Component Composition

Sometimes the best optimization is restructuring your components. Move state down to where it's actually used.

```tsx
// Bad: State at top level causes everything to re-render
function Dashboard() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <button onClick={() => setCount(count + 1)}>Count: {count}</button>
      <ExpensiveChart />
      <ExpensiveTable />
      <ExpensiveMap />
    </div>
  );
}

//Good: Isolate state in a separate component
function Dashboard() {
  return (
    <div>
      <Counter /> {/* Only this re-renders */}
      <ExpensiveChart />
      <ExpensiveTable />
      <ExpensiveMap />
    </div>
  );
}

function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>Count: {count}</button>;
}
```

## Code Splitting with React.lazy

Load components only when needed to reduce initial bundle size.

```tsx
import { lazy, Suspense } from "react";

// Lazy load heavy components
const HeavyChart = lazy(() => import("./HeavyChart"));
const AdminPanel = lazy(() => import("./AdminPanel"));

function App() {
  const [showChart, setShowChart] = useState(false);

  return (
    <div>
      <button onClick={() => setShowChart(true)}>Show Chart</button>

      {showChart && (
        <Suspense fallback={<div>Loading chart...</div>}>
          <HeavyChart />
        </Suspense>
      )}
    </div>
  );
}
```

## Virtualization for Long Lists

For lists with thousands of items, render only what's visible.

```tsx
import { FixedSizeList } from "react-window";

function VirtualizedList({ items }) {
  const Row = ({ index, style }) => (
    <div style={style}>{items[index].name}</div>
  );

  return (
    <FixedSizeList
      height={600}
      itemCount={items.length}
      itemSize={50}
      width="100%"
    >
      {Row}
    </FixedSizeList>
  );
}

// Renders only ~12 items instead of 10,000!
```

## Key Takeaways

1. **Understand before optimizing**: Profile first, optimize second
2. **React.memo**: Prevent unnecessary re-renders of pure components
3. **useMemo**: Cache expensive computations
4. **useCallback**: Stabilize function references for memoized children
5. **Component composition**: Move state closer to where it's used
6. **Code splitting**: Load code when needed, not upfront
7. **Virtualization**: Render only visible items in long lists
8. **Measure**: Use React DevTools Profiler to find real bottlenecks

## Common Mistakes to Avoid

### 1. Over-Memoization

```tsx
// Don't do this - premature optimization
const SimpleComponent = React.memo(({ text }) => <div>{text}</div>);

// This is fine without memo - it's cheap to render
const SimpleComponent = ({ text }) => <div>{text}</div>;
```

### 2. Wrong Dependencies

```tsx
// Missing dependencies
const value = useMemo(() => {
  return expensiveOperation(data, filter);
}, [data]); // Missing 'filter'!

// Correct dependencies
const value = useMemo(() => {
  return expensiveOperation(data, filter);
}, [data, filter]);
```

### 3. Inline Object/Array Props

```tsx
// Creates new object every render
<Component config={{ theme: "dark" }} />;

// Stable reference
const config = { theme: "dark" };
<Component config={config} />;

// Or use useMemo
const config = useMemo(() => ({ theme: "dark" }), []);
<Component config={config} />;
```
