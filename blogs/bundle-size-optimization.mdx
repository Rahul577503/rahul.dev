# Bundle Size Optimization: A Complete Investigation Guide

_Published on January 3, 2026_

A bloated JavaScript bundle is one of the fastest ways to kill your web app's performance. In this comprehensive guide, we'll explore how to investigate, analyze, and dramatically reduce your bundle size using proven techniques and real-world examples.

![Lighthouse Performance Score](/img/lighthouse-score.png)

**The result?** Lighthouse scores of 97+ and blazing-fast load times.

---

## Why Bundle Size Matters

Every kilobyte of JavaScript you ship to users has a cost:

- **Download time**: Users on slow connections wait longer
- **Parse time**: JavaScript must be parsed before execution
- **Execution time**: Large bundles take longer to run
- **Memory usage**: More code = more memory consumption

**Real Impact**:

- 100KB of JavaScript ≈ 1 second on 3G
- 500KB bundle can take 5-10 seconds to become interactive
- Each 100KB costs mobile users ~$0.10 in data charges

You can't optimize what you don't measure. Start by analyzing your current bundle size.

### Step 2: Identify the Culprits

After running the analyzer, you'll see a visual representation of your bundle. Look for:

**Red Flags**:

- Single packages > 100KB
- Duplicate libraries (same lib, different versions)
- Unused dependencies
- Entire libraries imported when only one function is needed

**Example Analysis**:

```
Total Bundle: 850KB
├─ node_modules/
│  ├─ moment.js (232KB) ⚠️ Too large!

│  └─ date-fns (45KB) ✅ Reasonable

│  └─ app code (346KB)
```

## Common Optimization Techniques

### 1. Replace Heavy Libraries

Many popular libraries have lighter alternatives:

```javascript
// Moment.js (232KB minified)
import moment from "moment";
const formatted = moment().format("YYYY-MM-DD");

// date-fns (13KB for what you use)
import { format } from "date-fns";
const formatted = format(new Date(), "yyyy-MM-dd");

// Or native Intl API (0KB - built-in)
const formatted = new Intl.DateTimeFormat("en-CA").format(new Date());
```

**Savings**: ~220KB (95% reduction!)

```javascript
// Lodash (full library: 71KB)
import _ from "lodash";
const unique = _.uniq(array);

// Lodash with tree-shaking (4KB per function)
import uniq from "lodash/uniq";
const unique = uniq(array);

// Native JavaScript (0KB)
const unique = [...new Set(array)];
```

**Savings**: ~67KB (94% reduction!)

---

### 2. Tree-Shaking and Dead Code Elimination

Modern bundlers automatically remove unused code, but you need to help them:

#### Good: Named Imports

```javascript
// Allows tree-shaking
import { Button, Input } from "my-ui-library";
```

#### Bad: Namespace Imports

```javascript
// Prevents tree-shaking - imports EVERYTHING
import * as UI from "my-ui-library";

// Even if you only use one component
<UI.Button />;
```

#### Real Example: React Icons

```javascript
// ❌ Bad: Imports ALL icons (156KB)
import * as Icons from "react-icons/fa";
<Icons.FaHome />;

// ✅ Good: Imports only what you need (2KB)
import { FaHome, FaUser } from "react-icons/fa";
<FaHome />;
```

**Savings**: ~154KB (98% reduction!)

### 3. Code Splitting

Don't send code users don't need immediately.

![Code Splitting Diagram](/img/code-splitting-diagram.png)

#### Route-Based Splitting

```javascript
//Bad: Everything in one bundle
import HomePage from "./pages/Home";
import DashboardPage from "./pages/Dashboard";
import SettingsPage from "./pages/Settings";

function App() {
  return (
    <Routes>
      <Route path="/" element={<HomePage />} />
      <Route path="/dashboard" element={<DashboardPage />} />
      <Route path="/settings" element={<SettingsPage />} />
    </Routes>
  );
}
```

```javascript
// Good: Split by route
import { lazy, Suspense } from "react";

const HomePage = lazy(() => import("./pages/Home"));
const DashboardPage = lazy(() => import("./pages/Dashboard"));
const SettingsPage = lazy(() => import("./pages/Settings"));

function App() {
  return (
    <Suspense fallback={<Loading />}>
      <Routes>
        <Route path="/" element={<HomePage />} />
        <Route path="/dashboard" element={<DashboardPage />} />
        <Route path="/settings" element={<SettingsPage />} />
      </Routes>
    </Suspense>
  );
}
```

**Result**:

- Initial bundle: 100KB (was 500KB)
- Each route chunk: ~50KB loaded on demand
- **80% faster initial load!**

#### Component-Based Splitting

```javascript
// ✅ Split heavy components
const HeavyChart = lazy(() => import("./components/HeavyChart"));
const VideoPlayer = lazy(() => import("./components/VideoPlayer"));
const RichTextEditor = lazy(() => import("./components/RichTextEditor"));

function Dashboard() {
  const [showChart, setShowChart] = useState(false);

  return (
    <div>
      <button onClick={() => setShowChart(true)}>Show Analytics</button>

      {showChart && (
        <Suspense fallback={<Spinner />}>
          <HeavyChart />
        </Suspense>
      )}
    </div>
  );
}
```

### 4. Dynamic Imports for Conditional Code

```javascript
// ✅ Load polyfills only when needed
async function loadPolyfills() {
  if (typeof window.IntersectionObserver === "undefined") {
    await import("intersection-observer");
  }

  if (!("fetch" in window)) {
    await import("whatwg-fetch");
  }
}

// Load features on demand
async function handleExport() {
  const { exportToExcel } = await import("./utils/export");
  exportToExcel(data);
}

// Load analytics only in production
if (process.env.NODE_ENV === "production") {
  import("./analytics").then(({ init }) => init());
}
```

### 5. Optimize Dependencies

#### Check for Duplicates

```bash
npm ls <package-name>
```

If you see multiple versions:

```
my-app@1.0.0
├─┬ package-a@1.0.0
│ └── lodash@4.17.21
└─┬ package-b@2.0.0
  └── lodash@4.17.20  ⚠️ Duplicate!
```

**Fix with resolutions** (package.json):

```json
{
  "resolutions": {
    "lodash": "4.17.21"
  }
}
```

#### Analyze Transitive Dependencies

```bash
npm ls --depth=3
```

Sometimes a small package pulls in huge dependencies:

```
my-package (5KB)
└── some-util (10KB)
    └── moment (232KB) ⚠️ Unexpected!
```

**Solution**: Find an alternative or fork and remove the dependency.

### 6. Webpack-Specific Optimizations

```javascript
// webpack.config.js
module.exports = {
  optimization: {
    // Split vendor code
    splitChunks: {
      chunks: "all",
      cacheGroups: {
        vendor: {
          test: /[\\/]node_modules[\\/]/,
          name: "vendors",
          priority: 10,
        },
        common: {
          minChunks: 2,
          priority: 5,
          reuseExistingChunk: true,
        },
      },
    },

    // Minimize code
    minimize: true,
    minimizer: [
      new TerserPlugin({
        terserOptions: {
          compress: {
            drop_console: true, // Remove console.logs
            drop_debugger: true,
          },
        },
      }),
    ],
  },

  // Externalize large libraries (load from CDN)
  externals: {
    react: "React",
    "react-dom": "ReactDOM",
  },
};
```

### 7. Next.js Optimizations

```javascript
// next.config.js
module.exports = {
  // Analyze bundle
  webpack: (config, { isServer }) => {
    if (!isServer) {
      config.optimization.splitChunks.cacheGroups = {
        ...config.optimization.splitChunks.cacheGroups,
        commons: {
          name: "commons",
          chunks: "all",
          minChunks: 2,
        },
      };
    }
    return config;
  },

  // Enable SWC minification (faster than Terser)
  swcMinify: true,

  // Optimize images
  images: {
    formats: ["image/avif", "image/webp"],
    deviceSizes: [640, 750, 828, 1080, 1200],
    imageSizes: [16, 32, 48, 64, 96],
  },

  // Remove unused CSS
  experimental: {
    optimizeCss: true,
  },
};
```

## Advanced Techniques

### 1. Barrel File Optimization

Barrel files (index.ts that re-export everything) can prevent tree-shaking:

```typescript
//  Bad: components/index.ts
export * from "./Button";
export * from "./Input";
export * from "./Modal";
// ... 50 more components

// When you import one component, bundler might include all
import { Button } from "./components";
```

```typescript
// Good: Import directly
import { Button } from "./components/Button";

// Or use named exports in barrel file
export { Button } from "./Button";
export { Input } from "./Input";
// Explicit exports help bundlers
```

## Conclusion

Bundle size optimization is not a one-time task—it's an ongoing process. Every dependency you add, every feature you build, affects your bundle size.

**Key Takeaways**:

1. **Measure first**: Use bundle analyzers to identify problems
2. **Replace heavy libraries**: There's usually a lighter alternative
3. **Code split aggressively**: Don't send code users don't need
4. **Enable tree-shaking**: Use named imports and ES modules
5. **Monitor continuously**: Set up size budgets and CI checks

Remember: **Every kilobyte counts**. A 100KB reduction might seem small, but it's the difference between a user staying or leaving.

Start optimizing today, and watch your Lighthouse scores soar! 🚀
