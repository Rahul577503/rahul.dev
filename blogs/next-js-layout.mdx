# Next.js Layouts: The Expert Architecture Guide

_Published on January 3, 2026_

Most tutorials show you *what* a layout is. This guide shows you *how engineers actually use them* — in SaaS products, dashboards, multi-tenant platforms, and content sites. By the end you'll have a mental model for designing a layout hierarchy before writing a single line of code.

---

## The Mental Model First

Before any code, understand what layouts *actually do* in the App Router.

```
  layout.tsx     → persists across route changes. State survives navigation.
  template.tsx   → re-mounts on every route change. Fresh state each time.
  page.tsx        → the unique content for that route.
  loading.tsx     → instant Suspense boundary (streamed skeleton).
  error.tsx       → error boundary for that segment.
  not-found.tsx   → 404 for that segment.
```

The key insight: **layouts are persistent shells, pages are swappable content.**

```
  Navigating /dashboard → /dashboard/settings:
  
  ┌──────────────────────────────────────────┐
  │  RootLayout          (never re-renders)  │
  │  ┌────────────────────────────────────┐  │
  │  │  DashboardLayout  (never re-renders│  │
  │  │  ┌──────────────────────────────┐  │  │
  │  │  │  page.tsx  ← only this swaps │  │  │
  │  │  └──────────────────────────────┘  │  │
  │  └────────────────────────────────────┘  │
  └──────────────────────────────────────────┘
```

This persistence is both the power and the trap. If you put subscription state in a layout, it survives navigation. If you accidentally put per-page state in a layout, it leaks between pages.

## Layout vs Template — When to Use Each

```
  layout.tsx                    template.tsx
  ──────────────────            ──────────────────────
  ✅ Sidebar state              ✅ Page enter animations
  ✅ Auth check (server)        ✅ Per-page analytics ping
  ✅ Navigation active state    ✅ form that must reset on nav
  ✅ Shared data fetching       ✅ Scroll position reset
  
  Mount count:  1               Mount count:  1 per navigation
```

```tsx
// template.tsx — re-mounts on every route change
// This is how smooth page transitions work
"use client";
import { motion } from "framer-motion";

export default function Template({ children }: { children: React.ReactNode }) {
  return (
    <motion.div
      initial={{ opacity: 0, y: 8 }}
      animate={{ opacity: 1, y: 0 }}
      transition={{ duration: 0.35, ease: [0.22, 1, 0.36, 1] }}
    >
      {children}
    </motion.div>
  );
}
```

## The Layout Hierarchy — How Nesting Works

Every file in the `app/` directory follows the same render order. Understanding this tree is everything.

```
  app/
  ├── layout.tsx          ← wraps EVERYTHING
  ├── template.tsx        ← re-mounts on each navigation
  ├── (home)/
  │   ├── layout.tsx      ← wraps all (home) routes
  │   ├── page.tsx        → /
  │   ├── about/
  │   │   └── page.tsx    → /about
  │   └── blog/
  │       ├── layout.tsx  ← wraps all blog routes
  │       ├── page.tsx    → /blog
  │       └── [slug]/
  │           └── page.tsx→ /blog/my-post
  └── dashboard/
      ├── layout.tsx      ← wraps all dashboard routes
      └── page.tsx        → /dashboard
```

**Render tree for `/blog/my-post`:**

```
  RootLayout
  └── HomeLayout
      └── BlogLayout
          └── BlogPostPage   ← only this changes between posts
```

**Render tree for `/dashboard`:**

```
  RootLayout
  └── DashboardLayout
      └── DashboardPage
```

The layouts between these two routes are *completely different*. The root layout is the only shared ancestor.

## Route Groups — The Organizing Pattern

Parentheses folders don't affect URLs. They let you **assign different layouts to different URL families** without polluting the URL.

```
  app/
  ├── (marketing)/          ← URL prefix: none
  │   ├── layout.tsx        ← marketing shell (navbar + footer)
  │   ├── page.tsx          → /
  │   ├── pricing/
  │   │   └── page.tsx      → /pricing
  │   └── blog/
  │       └── page.tsx      → /blog
  │
  ├── (auth)/               ← URL prefix: none
  │   ├── layout.tsx        ← centered card, no navbar
  │   ├── login/
  │   │   └── page.tsx      → /login
  │   └── register/
  │       └── page.tsx      → /register
  │
  └── (app)/                ← URL prefix: none
      ├── layout.tsx        ← sidebar + topbar, auth required
      └── dashboard/
          └── page.tsx      → /dashboard
```

Three completely different shells. Zero URL nesting. This is how every production SaaS is structured.

```tsx
// app/(auth)/layout.tsx — the login/register shell
export default function AuthLayout({ children }: { children: React.ReactNode }) {
  return (
    <div className="min-h-screen grid place-items-center bg-muted/30">
      <div className="w-full max-w-sm px-4">
        <div className="mb-8 text-center">
          <Logo />
        </div>
        <div className="rounded-xl border bg-card p-8 shadow-sm">
          {children}
        </div>
      </div>
    </div>
  );
}
```

```tsx
// app/(app)/layout.tsx — the authenticated app shell
import { redirect } from "next/navigation";
import { getSession } from "@/lib/auth";

export default async function AppLayout({ children }: { children: React.ReactNode }) {
  const session = await getSession();
  
  // Server-side auth guard — no client-side flicker
  if (!session) redirect("/login");

  return (
    <div className="flex h-screen overflow-hidden">
      <AppSidebar user={session.user} />
      <div className="flex flex-1 flex-col overflow-hidden">
        <AppTopbar user={session.user} />
        <main className="flex-1 overflow-y-auto p-6">
          {children}
        </main>
      </div>
    </div>
  );
}
```

```
  │   ├── page.tsx                → / (landing)
  │   ├── pricing/page.tsx        → /pricing
  │   └── changelog/page.tsx      → /changelog
  │
  ├── (auth)/
  │   ├── layout.tsx              ← centered auth card
  │   ├── login/page.tsx          → /login
  │   ├── register/page.tsx       → /register
  │   └── forgot-password/page.tsx→ /forgot-password
  │
  ├── (app)/
  │   ├── layout.tsx              ← auth guard + app shell
  │   ├── onboarding/
  │   │   ├── layout.tsx          ← full-screen stepper layout
  │   │   └── [step]/page.tsx     → /onboarding/workspace
  │   └── [org]/                  ← org slug in URL: /acme/...
  │       ├── layout.tsx          ← org context + sidebar
  │       ├── page.tsx            → /acme
  │       ├── projects/
  │       │   ├── page.tsx        → /acme/projects
  │       │   └── [id]/
  │       │       ├── layout.tsx  ← project nav tabs
  │       │       ├── page.tsx    → /acme/projects/abc
  │       │       └── settings/page.tsx → /acme/projects/abc/settings
  │       └── settings/
  │           ├── layout.tsx      ← settings sidebar nav
  │           ├── page.tsx        → /acme/settings
  │           └── billing/page.tsx→ /acme/settings/billing
  │
  └── (admin)/
      ├── layout.tsx              ← admin guard (role check)
      └── dashboard/page.tsx      → /admin/dashboard
```

The org-level layout is where the **multi-tenant** magic happens:

```tsx
// app/(app)/[org]/layout.tsx
import { notFound } from "next/navigation";
import { getOrg, getUserMembership } from "@/lib/db";
import { OrgContext } from "./context";

export default async function OrgLayout({
  children,
  params,
}: {
  children: React.ReactNode;
  params: Promise<{ org: string }>;
}) {
  const { org: slug } = await params;
  
  // Validate org exists
  const org = await getOrg(slug);
  if (!org) notFound();

  // Check user membership
  const membership = await getUserMembership(org.id);
  if (!membership) notFound(); // 404 rather than 403 — security best practice

  return (
    <OrgContext.Provider value={{ org, membership }}>
      <div className="flex h-full">
        <OrgSidebar org={org} membership={membership} />
        <div className="flex-1 overflow-auto">{children}</div>
      </div>
    </OrgContext.Provider>
  );
}
```

```
  │   └── [username]/

  │       ├── page.tsx            → /rahul (author home)
  │       └── [slug]/
  │           ├── layout.tsx      ← article shell (progress bar, ToC)
  │           └── page.tsx        → /rahul/my-post
  │
  └── (studio)/
      ├── layout.tsx              ← CMS/editor shell
      └── posts/
          ├── page.tsx            → /studio/posts (list)
          ├── new/page.tsx        → /studio/posts/new
          └── [id]/
              └── edit/page.tsx   → /studio/posts/abc/edit
```

The article layout with a reading progress bar:

```tsx
// app/(site)/[username]/[slug]/layout.tsx
"use client";
import { useEffect, useState } from "react";

export default function ArticleLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  const [progress, setProgress] = useState(0);

  useEffect(() => {
    const update = () => {
      const { scrollTop, scrollHeight, clientHeight } = document.documentElement;
      setProgress((scrollTop / (scrollHeight - clientHeight)) * 100);
    };
    window.addEventListener("scroll", update, { passive: true });
    return () => window.removeEventListener("scroll", update);
  }, []);

  return (
    <>
      {/* Reading progress bar */}
      <div
        className="fixed top-0 left-0 z-50 h-0.5 bg-foreground transition-all duration-100"
        style={{ width: `${progress}%` }}
      />
      {children}
    </>
  );
}
```

## Parallel Routes — Multiple Pages, One Layout

Parallel routes render multiple independent page segments in a single layout simultaneously. The `@` prefix marks a slot.

```
  dashboard/
  ├── layout.tsx
  ├── @overview/
  │   └── page.tsx     ← independent segment
  ├── @activity/
  │   └── page.tsx     ← independent segment
  └── page.tsx
```

```
  Layout receives all slots as props:
  
  ┌──────────────────────────────────────────────┐
  │  DashboardLayout                             │
  │  ┌─────────────────┐  ┌─────────────────┐   │
  │  │  @overview      │  │  @activity      │   │
  │  │  - has its own  │  │  - has its own  │   │
  │  │    loading.tsx  │  │    loading.tsx  │   │
  │  │    error.tsx    │  │    error.tsx    │   │
  │  │  - fetches      │  │  - fetches      │   │
  │  │    independently│  │    independently│   │
  │  └─────────────────┘  └─────────────────┘   │
  └──────────────────────────────────────────────┘
```

```tsx
// app/dashboard/layout.tsx
export default function DashboardLayout({
  children,
  overview,
  activity,
}: {
  children: React.ReactNode;
  overview: React.ReactNode;
  activity: React.ReactNode;
}) {
  return (
    <div className="grid grid-cols-3 gap-6">
      <div className="col-span-2">
        {overview}         {/* streams in independently */}
      </div>
      <div className="col-span-1">
        {activity}         {/* streams in independently */}
      </div>
    </div>
  );
}
```

**Why it matters:** each slot has its own `loading.tsx` and `error.tsx`. A slow activity feed won't block the overview. A crashed widget won't blank the whole dashboard. This is the pattern behind every production dashboard.

## Intercepting Routes — Modals with Shareable URLs

Open a photo in a modal. Share the URL. Recipient lands on the full photo page directly.

```
  app/
  └── photos/
      ├── [id]/
      │   └── page.tsx              ← /photos/1 (full page)
      └── @modal/
          └── (.)photos/
              └── [id]/
                  └── page.tsx      ← /photos/1 (modal if navigated from gallery)
```

```
  ┌─────────────────────────────────────────┐
  │  Photos Gallery (soft nav → shows modal)│
  │                                         │
  │  [photo] [photo] [photo]  ← click       │
  │               ↓                         │
  │  ┌──────────────────────────────────┐   │
  │  │          MODAL overlay           │   │
  │  │  URL: /photos/42                 │   │
  │  │  (gallery still visible behind)  │   │
  │  └──────────────────────────────────┘   │
  └─────────────────────────────────────────┘
  
  Direct URL visit /photos/42 → full page (no modal)
```

```tsx
// app/@modal/(.)photos/[id]/page.tsx
import Modal from "@/components/Modal";
import Photo from "@/components/Photo";

export default async function PhotoModal({
  params,
}: {
  params: Promise<{ id: string }>;
}) {
  const { id } = await params;
  const photo = await getPhoto(id);

  return (
    <Modal>
      <Photo photo={photo} />
    </Modal>
  );
}
```

```tsx
// app/layout.tsx — receives modal slot
export default function RootLayout({
  children,
  modal,
}: {
  children: React.ReactNode;
  modal: React.ReactNode;
}) {
  return (
    <html lang="en">
      <body>
        {children}
        {modal}    {/* null when not intercepted, modal when intercepted */}
      </body>
    </html>
  );
}
```

This pattern powers: Twitter photo lightboxes, Airbnb listing modals, Figma file preview panels.

## Server vs Client — The Layout Boundary

This is the #1 architectural decision in each layout. Get it wrong and you'll fight Next.js instead of leveraging it.

```
  Server Component layout:            Client Component layout:
  ──────────────────────────          ─────────────────────────────
  ✅ async/await (data fetch)         ✅ useState, useEffect
  ✅ Direct DB/filesystem access      ✅ Browser APIs
  ✅ Zero JS shipped to client        ✅ Event handlers
  ✅ Auth checks server-side          ✅ Real-time subscriptions
  ❌ No useState/useEffect            ❌ No async data fetching
  ❌ No browser APIs                  ❌ No direct DB access
```

**The pattern:** layouts are server components by default. Push client interactivity as far down the tree as possible.

```tsx
// app/dashboard/layout.tsx — Server Component (no "use client")
import { getSession } from "@/lib/auth";
import { ClientSidebar } from "./ClientSidebar"; // client boundary here

export default async function DashboardLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  // ✅ Direct server data access in a layout
  const session = await getSession();

  return (
    <div className="flex h-screen">
      {/* 
        ClientSidebar handles collapse toggle (useState).
        But the layout itself stays a Server Component.
        session is passed as a prop — serialized across the boundary.
      */}
      <ClientSidebar user={session.user} />
      <main className="flex-1 overflow-auto">{children}</main>
    </div>
  );
}
```

```tsx
// app/dashboard/ClientSidebar.tsx
"use client";
import { useState } from "react";

export function ClientSidebar({ user }: { user: User }) {
  const [collapsed, setCollapsed] = useState(false);

  return (
    <aside
      className={`transition-all ${collapsed ? "w-16" : "w-64"}`}
    >
      <button onClick={() => setCollapsed((c) => !c)}>
        {collapsed ? "→" : "←"}
      </button>
      {!collapsed && <UserMenu user={user} />}
    </aside>
  );
}
```

## Streaming Layouts — Show Shell Instantly

Without streaming: user waits for all data before seeing anything.
With streaming: shell renders immediately, data pops in as it resolves.

```
  Without streaming:
  
  [─────── wait for all data ───────────] [render entire page]
  
  With streaming + Suspense:
  
  [shell instant] [data A resolves] [data B resolves] [data C resolves]
       ↑                  ↑                 ↑                 ↑
   navbar loads       sidebar loads    main content       chart loads
   immediately          (200ms)           (400ms)           (600ms)
```

```tsx
// app/dashboard/page.tsx — streaming with independent Suspense boundaries
import { Suspense } from "react";
import { MetricsSkeleton, ActivitySkeleton } from "@/components/skeletons";

export default function DashboardPage() {
  return (
    <div className="grid gap-6">
      {/* Each Suspense boundary streams independently */}
      <Suspense fallback={<MetricsSkeleton />}>
        <MetricsCards />       {/* async server component */}
      </Suspense>

      <div className="grid grid-cols-2 gap-6">
        <Suspense fallback={<ActivitySkeleton />}>
          <RecentActivity />   {/* async server component */}
        </Suspense>

        <Suspense fallback={<div className="h-64 animate-pulse rounded-xl bg-muted" />}>
          <QuickStats />       {/* async server component */}
        </Suspense>
      </div>
    </div>
  );
}

// Each of these fetches its own data — no waterfall
async function MetricsCards() {
  const metrics = await getMetrics();  // Only this component waits
  return <div>{/* render metrics */}</div>;
}
```

## Metadata — Cascading Titles

Metadata in layouts sets the template. Pages override with their specific title.

```
  RootLayout:      { title: { template: "%s | Acme", default: "Acme" } }
  DashboardLayout: { title: { template: "%s | Dashboard · Acme" } }
  SettingsPage:    { title: "Settings" }
  
  Result: "Settings | Dashboard · Acme"
```

```tsx
// app/layout.tsx
export const metadata: Metadata = {
  title: {
    template: "%s | Acme",
    default: "Acme",           // Used when page has no title
  },
  description: "Project management for fast teams",
  metadataBase: new URL("https://acme.com"),
};

// app/(app)/dashboard/layout.tsx
export const metadata: Metadata = {
  title: {
    template: "%s | Dashboard",  // Nested template
  },
};

// app/(app)/dashboard/settings/page.tsx
export const metadata: Metadata = {
  title: "Settings",             // Final: "Settings | Dashboard"
};
```

## Performance Patterns

### Prefetch on Hover

```tsx
// Sidebar navigation — prefetch on hover for instant transitions
import Link from "next/link";

function NavItem({ href, label }: { href: string; label: string }) {
  return (
    // Next.js <Link> prefetches on hover by default in production
    <Link
      href={href}
      prefetch={true}   // explicit for clarity
      className="nav-item"
    >
      {label}
    </Link>
  );
}
```

### Layout Segment Config

```tsx
// app/dashboard/layout.tsx
// Control caching and runtime at the layout level
export const dynamic = "force-dynamic";  // never cache (user-specific data)
export const revalidate = 3600;          // revalidate every hour
export const runtime = "edge";           // run on edge network
```

### Avoid Prop Drilling with Layout Context

```tsx
// app/(app)/[org]/context.tsx
import { createContext, useContext } from "react";

type OrgContextValue = {
  org: Org;
  membership: Membership;
};

const OrgContext = createContext<OrgContextValue | null>(null);

export function OrgProvider({
  value,
  children,
}: {
  value: OrgContextValue;
  children: React.ReactNode;
}) {
  return <OrgContext.Provider value={value}>{children}</OrgContext.Provider>;
}

// Used anywhere inside the [org] subtree
export function useOrg() {
  const ctx = useContext(OrgContext);
  if (!ctx) throw new Error("useOrg must be used within OrgProvider");
  return ctx;
}
```

## Common Mistakes

### 1. Auth in Middleware AND Layout — Pick One

```tsx
// Bad: auth check in both middleware.ts and layout.tsx
// This is redundant and can cause subtle bugs

// Good: middleware for auth redirects (fast, edge)
// layout.tsx for data fetching based on auth
export function middleware(request: NextRequest) {
  const token = request.cookies.get("token");
  if (!token) return NextResponse.redirect("/login");
}

// Then in layout — fetch user data (not auth check again)
export default async function AppLayout({ children }) {
  const user = await getCurrentUser(); // already know they're authed
  return <Shell user={user}>{children}</Shell>;
}
```

### 2. Fetching in Layout What Should Be in Page

```tsx
// Bad: layout fetches page-specific data
// Now every route in this layout re-fetches this on navigation
export default async function DashboardLayout({ children }) {
  const stats = await getDashboardStats(); // ← belongs in the page
  return <div><Stats data={stats} />{children}</div>;
}

// Good: layout fetches layout-scope data only
export default async function DashboardLayout({ children }) {
  const user = await getUser();         // ← layout-scope: needed for sidebar
  return <Sidebar user={user}>{children}</Sidebar>;
}
```

### 3. "use client" on the Layout Itself

```tsx
// Bad: entire layout becomes client-side
"use client";
export default function Layout({ children }) { ... }

// Good: only the interactive part is client-side
// Server layout → client component leaf
export default function Layout({ children }) {
  return (
    <div>
      <ThemeToggle />    {/* "use client" lives in here */}
      {children}
    </div>
  );
}
```

## The Layout Decision Checklist

Before building any new layout, answer these:

- [x] Does this group of routes need a shared shell (nav, sidebar)?
- [x] Does this shell need server data (auth, user, org)?
- [x] Which parts need client interactivity (collapse, theme, modals)?
- [x] Does this layout need to auth-guard a route group?
- [x] Should any slots be independent (parallel routes)?
- [x] Do any navigations need to intercept into a modal?
- [x] What metadata template does this layout define?
- [ ] Have I kept layout data at layout-scope (not page-scope)?
- [ ] Is the server/client boundary as far down the tree as possible?

```
  │   └── register/
  │
  ├── (app)/              ← authenticated zone
  │   ├── layout.tsx      ← auth guard + redirect (Server)
  │   ├── onboarding/
  │   │   └── layout.tsx  ← stepper shell (Server)
  │   └── [org]/
  │       ├── layout.tsx  ← org guard + sidebar (Server + OrgProvider)
  │       ├── @modal/     ← intercepting modal slot
  │       ├── projects/
  │       │   └── [id]/
  │       │       ├── layout.tsx  ← project tabs (Server)
  │       │       └── @details/   ← parallel detail panel
  │       └── settings/
  │           └── layout.tsx  ← settings nav (Server)
  │
  └── (admin)/
      └── layout.tsx      ← role guard (Server)
```

This structure handles: marketing, auth, multi-tenant app, nested resources, modals, parallel panels, and admin — all with the right layout at the right level, server components by default, client components pushed to the leaves.

## Summary

Next.js layouts are not just "wrappers around pages." They are the primary tool for:

1. **Route group isolation** — different shells for marketing, auth, and app without URL pollution
2. **Server-side auth** — guard routes at the layout level with no client flicker
3. **Multi-tenant context** — validate org/workspace and provide context to all child routes
4. **Parallel rendering** — independent slots with their own loading/error states
5. **Modal routing** — shareable URLs that render as modals when navigated, full pages when linked directly
6. **Streaming** — ship the shell instantly, stream content as it resolves

The engineers who get the most out of Next.js are the ones who design the layout hierarchy *before* writing any component code. Draw the tree first. The code follows naturally.
