# Mastering Design Patterns for Backend Development: A Comprehensive Guide

_Published on February 22, 2025_

## 1. Creational Patterns: Building Objects Smartly

Creational patterns focus on flexible and reusable object creation. They help you manage how objects are instantiated, ensuring your backend systems remain efficient and adaptable.

### a. Singleton Pattern: One Instance, Global Access

The Singleton pattern ensures a class has only one instance and provides a global point of access to it. It’s perfect for resources like database connections or logging services in backend systems.

```js
class Singleton {
    static instance = null;

    constructor() {
        if (Singleton.instance) return Singleton.instance;
        Singleton.instance = this;
    }

    static getInstance() {
        if (!Singleton.instance) {
            Singleton.instance = new Singleton();
        }
        return Singleton.instance;
    }

    showMessage() {
        console.log("Singleton instance is working!");
    }

}
```


**Use Case**: Use Singleton for a database connection pool in a backend API to ensure only one manager handles connections, reducing resource overhead.

### b. Factory Method Pattern: Creating Objects Flexibly

This pattern defines an interface for creating objects but lets subclasses decide which class to instantiate. It’s ideal for creating different types of objects, like database queries, without hardcoding their classes.

```js
class DatabaseQuery {
    execute() {}
}

class SQLQuery extends DatabaseQuery {
execute() {
console.log("Executing SQL query...");
}
}

class NoSQLQuery extends DatabaseQuery {
execute() {
console.log("Executing NoSQL query...");
}
}

class QueryFactory {
static createQuery(type) {
if (type === 'sql') return new SQLQuery();
if (type === 'nosql') return new NoSQLQuery();
throw new Error("Unknown query type");
}
}
```

**Use Case**: Use Factory Method in a backend API to create SQL or NoSQL queries based on the database type, enhancing flexibility.

## 2. Structural Patterns: Composing Objects Effectively

Structural patterns deal with object composition and relationships, helping you build robust backend systems by connecting interfaces and classes.

### a. Adapter Pattern: Bridging Incompatible Interfaces

The Adapter pattern lets incompatible interfaces work together by converting one interface into another that a client expects. It’s great for integrating legacy systems or third-party APIs.

```js
class PaymentProcessor {
    processPayment(amount) {}
}

class LegacyPaymentSystem {
makePayment(amount) {
console.log("Processing payment of $" + amount + " via legacy system.");
}
}

class PaymentAdapter extends PaymentProcessor {
constructor(legacySystem) {
super();
this.legacySystem = legacySystem;
}

    processPayment(amount) {
        this.legacySystem.makePayment(amount);
    }

}
```

```md
| - processPayment| | - legacySystem |
+----------------+ +----------------+
^
|

+----------------+
```

**Use Case**: Use Adapter in a backend payment system to integrate a legacy payment gateway with a modern interface.

### b. Facade Pattern: Simplifying Complexity

The Facade pattern provides a simplified interface to a complex subsystem, hiding its intricacies. It’s ideal for coordinating multiple backend services or APIs.

```js
class PaymentService {
    process() {
        console.log("Processing payment...");
    }
}

class NotificationService {
send() {
console.log("Sending notification...");
}
}

class LoggingService {
log() {
console.log("Logging transaction...");
}
}

class TransactionFacade {
constructor() {
this.payment = new PaymentService();
this.notify = new NotificationService();
this.log = new LoggingService();
}

    executeTransaction() {
        this.payment.process();
        this.notify.send();
        this.log.log();
    }

}
```

## 3. Behavioral Patterns: Managing Object Communication

Behavioral patterns focus on communication between objects, enabling flexible and maintainable backend logic.

### a. Observer Pattern: Real-Time Notifications

The Observer pattern establishes a one-to-many dependency, notifying all dependent objects of state changes. It’s perfect for real-time updates in backend systems.

```js
class Subject {
    constructor() {
        this.observers = [];
    }

    registerObserver(observer) {
        this.observers.push(observer);
    }

    removeObserver(observer) {
        this.observers = this.observers.filter(obs => obs !== observer);
    }

    notifyObservers(message) {
        this.observers.forEach(observer => observer.update(message));
    }

}

class Observer {
constructor(name) {
this.name = name;
}

    update(message) {
        console.log(`${this.name} received news: ${message}`);
    }

}

class NewsAgency extends Subject {
setNews(news) {
this.news = news;
this.notifyObservers(news);
}
}
```

### b. Strategy Pattern: Switching Algorithms at Runtime

The Strategy pattern defines a family of algorithms, encapsulates each, and makes them interchangeable at runtime. It’s useful for backend logic needing flexible behavior, like sorting or pricing.

```js
class SortingStrategy {
    sort(list) {}
}

class BubbleSortStrategy extends SortingStrategy {
sort(list) {
console.log("Sorting using Bubble Sort...");
for (let i = 0; i < list.length - 1; i++) {
for (let j = 0; j < list.length - i - 1; j++) {
if (list[j] > list[j + 1]) {
[list[j], list[j + 1]] = [list[j + 1], list[j]];
}
}
}
}
}

class QuickSortStrategy extends SortingStrategy {
sort(list) {
console.log("Sorting using Quick Sort...");
if (list.length <= 1) return list;
const pivot = list[Math.floor(list.length / 2)];
const left = [], right = [], equal = [];
for (let element of list) {
if (element < pivot) left.push(element);
else if (element > pivot) right.push(element);
else equal.push(element);
}
return [...this.sort(left), ...equal, ...this.sort(right)];
}
}

class Sorter {
constructor() {
this.strategy = null;
}

    setStrategy(strategy) {
        this.strategy = strategy;
    }

    performSort(list) {
        if (this.strategy) this.strategy.sort(list);
    }

}
```

```md
| - setStrategy()| +----------------+
| - performSort()| ^
+----------------+ |
+----------------+ +----------------+
| BubbleSortStrategy| | QuickSortStrategy|
| - sort() | | - sort() |
+----------------+ +----------------+
```

**Use Case**: Use Strategy in a backend analytics system to switch sorting algorithms based on data size or performance needs.

## 4. Concurrency Patterns (Java-Specific): Handling Multithreading

Concurrency patterns manage multi-threaded or asynchronous operations, critical for performant backend systems.

### a. Thread Pool Pattern: Efficient Task Execution

The Thread Pool pattern reuses a pool of threads to execute tasks, avoiding the overhead of creating new threads. It’s essential for backend servers handling multiple requests.

```js
const { Worker, isMainThread, parentPort } = require('worker_threads');
if (isMainThread) {
    const pool = [];
    for (let i = 0; i < 3; i++) {
        pool.push(new Worker(__filename));
    }

    let taskId = 0;
    pool.forEach(worker => {
        worker.postMessage({ task: `Task-${++taskId}` });
        worker.on('message', (message) => {
            console.log(message);
        });
    });

} else {
parentPort.on('message', (task) => {
console.log(`Executing ${task.task} on thread ${process.pid}`);
setTimeout(() => {
parentPort.postMessage(`Done: ${task.task}`);
}, 1000);
});
}
```

**Use Case**: Use Thread Pool in a backend server to handle HTTP requests efficiently without creating a new thread per request.

### b. Future/Promise Pattern: Asynchronous Results

This pattern manages asynchronous results, allowing the program to continue while waiting for a result. It’s ideal for backend I/O operations or API calls.

```js
function asyncTask() {
    return new Promise((resolve) => {
        setTimeout(() => {
            resolve("Task completed!");
        }, 2000);
    });
}

async function main() {
console.log("Doing other work while task runs...");
await new Promise(resolve => setTimeout(resolve, 1000));
const result = await asyncTask();
console.log("Result: " + result);
}

main();
```

## 5. Architectural Patterns: Structuring Your System

Architectural patterns define the overall structure of software systems, ensuring scalability and maintainability in backend development.

### a. MVC (Model-View-Controller) Pattern: Separating Concerns

MVC separates data (Model), user interface (View), and business logic (Controller). It’s widely used in backend and web development for clean, scalable code.

```js
class User {
    constructor(name, age) {
        this.name = name;
        this.age = age;
    }

    getName() { return this.name; }
    getAge() { return this.age; }

}

class UserView {
displayUser(user) {
console.log(`User: ${user.getName()}, Age: ${user.getAge()}`);
}
}

class UserController {
constructor(model, view) {
this.model = model;
this.view = view;
}

    updateView() {
        this.view.displayUser(this.model);
    }

    setUserName(name) {
        this.model = new User(name, this.model.getAge());
    }

    setUserAge(age) {
        this.model = new User(this.model.getName(), age);
    }

}
```


**Use Case**: Use MVC in a backend REST API to separate database logic, API endpoints, and response formatting.

### b. Microservices Pattern: Loosely Coupled Services

Microservices build applications as independent, loosely coupled services. It’s ideal for scalable backend systems, especially in cloud environments.

```js
// User Service (Express.js example)
const express = require('express');
const app = express();

app.get('/users/:id', (req, res) => {
const user = { name: 'John', age: 30 };
res.json(user);
});

app.listen(3000, () => console.log('User Service running on port 3000'));

// Order Service (Express.js example)
const orderApp = express();

orderApp.post('/orders', (req, res) => {
const order = req.body;
res.json(order);
});

orderApp.listen(3001, () => console.log('Order Service running on port 3001'));
```

**Use Case**: Use Microservices in an e-commerce backend to separate user management, order processing, and payment services for independent scaling.
